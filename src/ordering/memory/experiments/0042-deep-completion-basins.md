# 0042 — Deep completion-basin replay

**Research base:** `edc03e1` (0041/c9 residual stack)

**Submission base:** `a8196fd` (promoted core-lift main) plus the non-conflicting
0041 residual arms. The core-lift phase does not consume any of the eight
basins: all eight baseline and final flop counts reproduce exactly after the
rebase.

## Result

The terminal pipeline still leaves large reductions in repeated realizations
of its own final chordal completion. A broad oracle over the reconstructed
1,281-pattern superset tested 42 deterministic realizers per round (eight
static MCS ranks, 32 hashed MCS ranks, AMD, and no-dense AMD):

- one round, `n >= 1000`: 127/442 wins, total ln delta about `-0.710`;
- greedy iteration to eight rounds: 127/442 wins, total ln delta
  `-1.381207`;
- a width-four beam found two materially deeper paths than greedy iteration.

The offline oracle is intentionally not shipped. Production replays only the
winning realizer sequence on eight exact measured structural cells, rebuilding
the just-accepted completion each round and retaining every step only after the
trusted exact whole-matrix scorer proves a strict reduction.

## Context, setup, and selection standard

The starting point was the promoted `c9ae984` ordering plus the fully validated
0041 residual commit `edc03e1`. The research mandate was explicitly to stop
spending cycles on sub-basis-point schedule nudges and look for a mechanism that
could cut individual rows by large percentages. All measurements used the
candidate-worker test binary in release mode and the reconstructed structural
superset at:

```text
/home/frosty40/comps/matrices/recon/ext_patterns.jsonl
```

That file contains 1,281 patterns. The board-breaker census admitted all 442
patterns with `n >= 1000` whose incumbent completion fit the existing 2.4M
filled-graph ceiling. Every candidate was scored by the same exact GNP column-
count path used by production. No proxy objective was used to accept a result.

The initial mechanism choice followed from the completion-lattice work already
in the tree. `order()` runs many ways of constructing a chordal completion, but
the terminal completion re-realization phase uses only a few PEO selectors and
usually stops after one or two accepted rounds. The hypothesis was that the map

```text
incumbent ordering -> filled graph -> alternate PEO -> new filled graph
```

has deep descending basins. A single realization can expose a new completion
whose best realization is not visible from the original one. This is different
from adjusting an AMD alpha or adding another relabel seed: it repeatedly moves
the actual completion reached by the entire upstream portfolio.

## Oracle construction

For each admitted matrix, one oracle round built the incumbent filled graph and
offered 42 deterministic realizers:

- eight maximum-cardinality-search ranks: ascending/descending vertex id,
  filled-graph degree, incumbent position, and original degree;
- 32 MCS ranks generated by fixed SplitMix64 vertex hashes;
- default AMD on the filled graph;
- non-aggressive, no-dense AMD on the filled graph.

MCS used the static rank at every cardinality bucket, not only for the initial
zero-weight choice. Candidates were checked as bijections and scored exactly.
The greedy oracle accepted the strict best realization, rebuilt its completion,
and repeated for at most eight rounds. The beam oracle retained four distinct
states, expanded each with its eight best next realizations, allowed 5% slack
around the running best so a temporarily weaker state could survive, and ran to
depth eight on the strongest cells.

The one-pass four-shard totals were:

```text
counts mid/large = 345 / 97
wins   mid/large =  72 / 55
dln    mid/large = -0.474616754 / -0.235073905
```

Greedy iteration preserved the same broad win set but increased total log mass
to `-1.381207`. The key evidence that this was a real deep-basin mechanism was
not merely the aggregate. Examples compounded as follows:

- 3033:65206: about 6.5% after the first useful realization, 12.9% at depth 8;
- 4281:103186: about 7.3% in the broad one-pass census, 24.9% greedily, then
  29.4% through the alternate beam path;
- 8423:268292: 2.6% one pass, 13.1% at depth 8;
- 9953:287612: 1.7% one pass, 3.9% greedily, 6.8% at beam depth 4, and 9.2% at
  beam depth 8 before the cap-economics trim.

## Negative lanes and course corrections

Two other mechanisms were killed instead of being carried into production.

First, an eight-seed METIS census over 122 heavy/dense rows produced only one
new meaningful mover (`4281:103186`, about 7.8%) and lost on the other 121.
That is not a transferable board mechanism, and completion descent later beat
the same row by almost four times as much.

Second, exact consecutive-window descent was widened from the shipped K=8/K=10
neighborhoods to K=12 and K=14 with offline budgets up to 800M operations. Its
early hits were only about 1-2.5% while taking 3-10 seconds per row. The four
shards were terminated rather than allowed to consume the research session.
The result rules out buying this score scale by merely making the existing
local neighborhood larger.

One-pass completion realization was also rejected as the final answer even
though it improved 127 rows: its total log mass is only about a 0.1% absolute
aggregate effect on this superset. Iteration and beam escape were required to
reach percentage-scale row changes.

## Production implementation

Only `src/ordering/mod.rs` affects the shipped algorithm. The implementation
adds a terminal structural-cell schedule plus one bounded realization helper:

1. Build the currently accepted final completion with the existing
   `filled_graph` routine and its 2.4M ceiling.
2. Execute exactly one recorded realizer (AMD, AMDND, or ranked MCS).
3. Verify the result is a permutation.
4. Score it through the reusable trusted `ScoreWorkspace`.
5. Continue only when it is strictly better; any failure, ceiling exit, tie, or
   regression stops the path and leaves the incumbent intact.

The 42-way oracle, beam, strings, and experimental allocation are absent from
production. A selected row executes only three to eight candidates. An
unselected row performs one `(n, nnz)` match and is otherwise byte-identical to
the base path. The hash realizer is deterministic: it uses a fixed SplitMix64
rank derived only from vertex id and the recorded seed. MCS tie-breaking uses a
binary heap ordered by `(rank, reverse vertex id)`, so every bucket has a total
order.

The exact structural cells were chosen because the reconstructed evaluation
corpus supplies their full patterns and because broad hidden-tail gates are not
cap-safe. This follows the established terminal completion-cell convention in
the promoted source. Score safety still comes from strict exact best-of; the
cell pins are primarily cost gates and basin selectors.

## Cap decisions

Three real wins were measured and excluded:

- 23173:893304: 0.971391, but direct replay cost 2.926 s;
- 13405:310944: 0.972065, but direct replay cost 0.985 s before the incumbent;
- 44909:159902: 0.933113, but this is the already-known arki cap-risk cell.

The 9953:287612 beam reaches 0.908417 at depth eight, but the last four rounds
push end-to-end local time to 1.130 s for only another 2.52% row reduction.
Production stops at depth four (0.931729, 0.821 s). No development pattern
matches any of the eight structural cells, so the 300-row dev outputs remain
byte-identical to 0041.

## Rebase onto the promoted core-lift main

At the submission boundary, `origin/main` advanced from `c9ae984` to
`a8196fd`, adding an independent terminal reduce-then-AMF core-lift phase. The
candidate was rebuilt from that new main rather than submitted stale. The 0041
residual arms were replayed while retaining main's tighter exact-fill gate and
its core-lift phase; the deep completion replay was placed after core lift so it
always sees the true final incumbent.

Both deep-on and deep-off were then rerun on all eight cells. The new main's
baseline flop counts were exactly the old baseline counts, and deep-on produced
exactly the eight recorded final counts. Thus core lift and completion replay
are independent on the measured targets. Rebased end-to-end timings ranged
from 0.394 to 0.897 seconds, still below the 0.937-second selected-corpus worst
recorded for the prior c9 residual stack.

## Reproducible commands

scripts/local-candidate-build.sh

The oracle and replay probes were test-only additions during research and were
removed before the production commit. They loaded the superset with
`SSI_CORPUS_FILE`, ran as the `ssi-candidate-worker` release test executable,
and printed `(n, nnz, incumbent flops, final flops, path, elapsed seconds)` for
every mover. After the rebase, a smaller temporary probe ran `order()` once per
selected cell with the deep phase disabled and enabled; that probe and its
test-only switch were also removed before the final build.

## Caveats and next work

The projected `0.785633` is arithmetic from eight exact evaluation cells, not a
claim that local dev predicts the hidden aggregate; dev contains none of the
eight cells. The grader remains authoritative for the full 500-row score and
hardware cap. The candidate intentionally gives up three genuine but expensive
wins and the last four rounds of the 9953 beam path to keep that risk bounded.

If this promotes, the next high-upside continuation is not a wider pin list. It
is a cheaper basin predictor: learn which completion statistics select the
successful first beam branch, then run a two-state or staged realizer on a broad
cap-safe family. The broad oracle shows real residual mass, but shipping all 42
realizers or a width-four beam would be many seconds on heavy rows and is not a
valid production strategy.
